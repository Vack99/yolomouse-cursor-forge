# Lessons

Patterns discovered while in debugging mode. Append-only.

## 2026-05-15 — GIF transparency, perceived shape bugs

**Pattern: attaching ANY PropertyItem to a bitmap suppresses GDI+'s auto-detection of the transparent palette index.**
GDI+'s GIF encoder normally inspects alpha=0 pixels and marks a palette entry transparent via the GCE (Graphic Control Extension) packed flag. The moment you call `SetPropertyItem(0x5100)` (FrameDelay) — or any other property — that auto-detection is bypassed and every frame's GCE drops its transparency flag. The cure: explicitly set `0x5104` (`PropertyTagIndexTransparent`) on **every** frame, including each one passed to `SaveAdd`, not just frame 0. Setting it only on the first frame leaves frames 1..N-1 opaque.

**Pattern: `Bitmap.GetPixel` on a decoded GIF lies about transparency.**
When System.Drawing decodes a GIF, `GetPixel` returns the palette color for "transparent" pixels regardless of whether the GCE flag is set. So a GIF that displays as a solid black square in Edge will report `A=255 R=0 G=0 B=0` from `GetPixel` — looks like "opaque black pixel," looks like a non-bug. To actually prove transparency works: parse the raw GCE bytes (`21 F9 04 <packed>`), or composite the GIF over a colored canvas via `Graphics.DrawImage` and sample the result. The composite test is what real viewers do.

**Pattern: when a user says a cursor "looks like only half a pointer," check the rendering chain (PNG vs strip vs GIF vs YoloMouse-installed) before redesigning the shape.**
In this session the cursor shape was correct (head + vertical stem matching the modern macOS pointer); the apparent missing-stem was caused by the dark-purple stem pixels being invisible against the GIF's opaque-black background after BUG-01. A speculative shape redesign (diagonal stem instead of vertical) would have produced a Windows-Aero / teardrop silhouette, not a Mac pointer, and would have collapsed the rainbow stripes from cross-diagonal bands into longitudinal streaks. Defer shape changes until the rendering pipeline is verified clean and the user re-confirms with fresh eyes.

**Pattern: PowerShell 5.1 `[int](5/2) = 2`, but `[int](2.5) = 2` and `[int](3.5) = 4`.**
PowerShell uses banker's rounding for `[int]` casts on floats — half-to-even. This silently produces off-by-one stripe indices when computing palette positions via integer division. Use `[Math]::Floor($x / 2)` for true truncation.

**Residual risks to monitor:**
- The 0x5104 fix relies on the same Activator-private-constructor trick that builds the loop-count PropertyItem. If a future host blocks reflection-based construction, the GIF will silently revert to opaque background (the existing single-frame fallback still kicks in for total encoder failure, but the no-transparency case sits in between). Worth a single explicit test that probes a known-transparent pixel post-build if/when the test suite grows to cover GIF output.
- The cursor shape (`projects/MacRainbow/frames/frame_NN.grid.txt`) is identical across all 12 frames — only interior letters shift. Any future shape change is a 12-file edit; consider regenerating via the same script in `projects/MacRainbow/design.md` rather than hand-editing.

## 2026-05-20 — Cursor Studio first-launch failures

**Pattern: `useCallback` / `useState` / `useEffect` placed *after* an early `return` from a React component crashes the tree as a black-screen flash, not a stack trace.**
React 18 production builds enforce rules-of-hooks by tracking the hook position per render. If render 1 has N hooks (because state was `loading` and the component bailed at `if (state.status === 'loading') return ...`) and render 2 has N+1 (because state flipped to `ready` and execution flows past the early return into a misplaced `useCallback`), React detects the position mismatch, throws, and unmounts the entire tree. Body's dark background shows through and the page reads as black. The console shows the actual error, but vitest's isolation tests and Node-side server smoke tests never render the React tree, so this class of bug ships green. The cure is mechanical: every `useState` / `useEffect` / `useCallback` / `useReducer` / `useMemo` / `useRef` must be unconditionally called *before* any conditional return. When a hook needs values that only exist post-load, lift the hook above and check `state.status !== 'ready'` inside the callback body. Don't trust eyeballing — use `eslint-plugin-react-hooks`'s `rules-of-hooks` rule, which is now wired into `pnpm --dir studio lint`.

**Pattern: `Set-Content -Encoding utf8` in PowerShell 5.1 prepends a UTF-8 BOM that Node's `JSON.parse` rejects with `Unexpected token '﻿'`.**
PS 5.1 has no `utf8NoBOM` encoding; the `utf8` value writes EF BB BF then the content. Any JSON file written this way fails the studio server's first read with an opaque "unexpected token" error pointing at the invisible BOM glyph. Diagnose with `xxd <file> | head -1` — leading `efbbbf` means BOM present. Cure: `[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding $false))`. The harness's PowerShell notes warn about UTF-16 LE BOM as the default; the trap is that the `utf8` opt-in also writes a BOM in 5.1, just a different one. Confirmed via byte-level diff between a working hand-authored fixture (`projects/TracerDot/palette.json`, no BOM) and the first `forge canvas-new` output (`efbbbf` prefix). Tests should assert `byte[0] -ne 0xEF` to pin the absence going forward.

**Pattern: `2>&1` or `2>$null` on a native exe in PS 5.1 wraps stderr lines as `NativeCommandError` records that re-throw under `$ErrorActionPreference = 'Stop'`.**
The test runner sets `$ErrorActionPreference = 'Stop'`, which is correct for cmdlets. But calling `& powershell -File .\forge.ps1 ...` with `2>&1 | Out-String` or `2>$null` re-enters the parent host's error stream with each stderr line wrapped as a `NativeCommandError`, which the EAP=Stop machinery treats as terminating and re-throws into the test body — even when the exe returned a non-zero exit cleanly and `$LASTEXITCODE` would have told the truth. Symptom: a Pester `Test-Case` "FAIL"s with the inner script's exact throw message, no matter what the Assert-True regex checks. Cure: don't redirect stderr from a native exe in a test that runs under EAP=Stop. Either invoke the script in-process with `& .\forge.ps1 <args>` and wrap in `try/catch`, or accept the stderr noise in test output and assert only against `$LASTEXITCODE` + side-effects. The harness's PowerShell notes call this out — heed them.
